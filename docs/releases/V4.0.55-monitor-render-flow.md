# V4.0.55 — Bound native Monitor render work and capture market-flow evidence

User reports all App prices stop while floating Monitor is open and recover immediately on closing it. Review found no direct foreground subscription pause caused by opening Monitor. The known load defect is per-snapshot service intents: JavaScript sync promises resolve before main-thread onStartCommand performs a full view rebuild, so JS latest-job coalescing does not bound the Android work queue. No device trace yet proves this is the sole phone cause.

## Scope / acceptance
- Existing visible Monitor receives event-driven latest-frame refresh with at most one queued callback, rather than service start per quote. First open/restore still uses the service. Closed windows cannot be reopened by a queued draw.
- Preserve configuration/mode/layout. Do not repaint desktop Widget twice, or rewrite identical Monitor config for every quote.
- Compile and run production Kotlin queue: 1000 quote burst, latest value, burst during draw, 8 concurrent producers, close/cancel and render-error recovery. Wiring smoke separate.
- Bounded diagnostic checkpoints on open, once after 2 seconds, close and once after 1.5 seconds record source/bridge/App/draw counts and durations, not quote values or portfolio details. No price requests or repeat sampling. Existing error log exports these MARKET_FLOW entries. JS counters include appReceiptAt and represent receipt/replay time, not the original native checkpoint time.
- Full 146 inherited regression gates, TypeScript, GitHub backend/quality/native QA, APK digest/package/version/permissions/native classes validation.
- Phone acceptance pending: open wall while App foreground, observe later trades, close wall, export error log if still frozen. Compare native trades/snapshots with App applied counts and render/probe delay. Do not claim full freeze fixed without phone result.
